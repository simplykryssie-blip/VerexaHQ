# Future Enhancements

Ideas identified during the beta-readiness completion pass that are genuine improvements but out of scope for this pass — either because they're new feature work rather than a bug fix, or because they're a larger UX investment than a targeted polish change. Not implemented per the pass's own rule: audit and fix, don't invent new workflows.

| # | Idea | Benefit | Estimated effort | Priority |
|---|---|---|---|---|
| 1 | Document versioning UI. `documents.version_number`, `.replaces_document_id`, `.is_latest_version` all exist in the schema, but no frontend code reads or writes them — uploading a new version of an existing document just creates an unrelated row today. | Lets staff/clients replace a document without losing history, and see prior versions. | Medium (upload-replaces-existing flow, version history list, "restore" action) | Medium |
| 2 | Document folder rename/delete. `DocumentFolderModal` only creates folders (from a template or manually) — there's no way to rename or delete one afterward. | Completes basic folder management instead of only supporting one-way creation. | Small–Medium | Low |
| 3 | Replace `window.prompt()` for document-rejection reason with a proper on-brand modal (text input + Cancel/Reject buttons), matching the `ConfirmDialog` pattern already used everywhere else for destructive actions. | Consistent, accessible, on-brand UI instead of an unstyled native browser prompt that some browsers/extensions block. | Small (new small modal component) | Low |
| 4 | Deeper template systems beyond form templates. The app's nav labels `/forms` as "Templates," and that page is the only template management UI that exists. Confirmed via production schema that `email_templates`, `workflow_blueprints`, `document_templates`, and `message_templates` tables all exist but have **zero frontend usage** — no read, no write, no UI anywhere. `service_templates` and `document_request_templates` are consumed (read-only, correctly) when activating a service or applying a document-folder template, but have no management UI of their own either. There's no merge-field/document-generation system implemented anywhere in the frontend. | Would let the firm manage reusable email copy, generate documents from templates with client data merged in, and build multi-step workflow blueprints instead of relying on manual task creation. | Large (each is its own feature: an email-template editor, a document-generation engine with merge-field syntax, a workflow-blueprint builder, and CRUD UI for service/document-request templates) | Medium — valuable but each item here is a multi-week feature, not a quick add |
| 5 | Team member management (invite, role change, deactivate). Settings → Team currently only lists existing `workspace_members` read-only. `workspace_member_invitations` exists in the schema, but no frontend code reads or writes it, and there's no UI to invite a new team member, change someone's role, or deactivate them. | Lets a firm actually onboard staff without a database console. | Medium (invite flow + email, role editor, deactivate action) | High — this blocks a firm from adding any team member beyond the one that signs up |
